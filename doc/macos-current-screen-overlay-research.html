FloatClock：macOS 当前屏幕与全屏 Space 显示方案调研

调研日期：2026-08-17 · 项目分支：feature/refactor_in_compose · Compose Multiplatform 1.8.2
实施状态（2026-08-17）

推荐方案已经实现并完成一次多屏修正：应用为每个物理显示器创建一个非激活 NSPanel，再通过 macOS 原生桥接修改其 collectionBehavior；macOS 13+ 使用 canJoinAllApplications + canJoinAllSpaces，旧系统使用 canJoinAllSpaces + fullScreenAuxiliary。桥接已通过 Kotlin/Objective-C 构建、JAR 资源检查、DMG 打包和运行验证。

结论

这个需求包含两个独立问题：① 把窗口定位到“当前显示器”；② 让窗口有资格进入其他 App 的全屏 Space。第一个问题用公开 AWT API 即可解决；第二个问题的可靠解法是给底层 NSWindow 设置 AppKit 的 collection behavior。

推荐实现：macOS 13+ 使用 canJoinAllApplications + canJoinAllSpaces，保留 AWT alwaysOnTop 对应的 floating level；macOS 12 及以下降级为 canJoinAllSpaces + fullScreenAuxiliary。先用 Window.Type.POPUP 做零原生代码 PoC，但不把它当作跨应用全屏的最终保证。

1. 项目当前实现与缺口

  • 实际打包入口是 top.ntutn.floatclock.FloatClock，使用 Compose Desktop DialogWindow，底层仍是 AWT ComposeDialog/JDialog。
  • 当前只设置了 alwaysOnTop = true。OpenJDK 在 macOS 上仅将它映射为 NSFloatingWindowLevel；窗口层级高，不等于窗口被允许进入另一个 Space。
  • WindowPosition(Alignment.BottomEnd) 依赖 Compose 创建窗口时选中的 GraphicsConfiguration。Compose 1.8.2 默认只跟踪本应用上次获得焦点的窗口；本项目首次启动且没有本应用焦点历史时会回到默认显示器，而不是鼠标或其他 App 的当前显示器。
  • 未设置 NSWindow.collectionBehavior，因此没有“所有桌面”“加入其他应用”“全屏辅助窗口”语义。
  • 当前 DialogWindow 未传 focusable = false；作为时钟覆盖层，建议禁止抢焦点。

2. macOS 原生机制

API作用适用性
NSWindowCollectionBehaviorCanJoinAllApplications
macOS 13+		允许窗口加入其他 App 的窗口集合和符合条件的全屏 Space；Apple 明确建议浮动窗口和系统覆盖层使用。最匹配本需求
NSWindowCollectionBehaviorCanJoinAllSpaces
macOS 10.5+		窗口可出现在所有 Space。它解决桌面切换，不单独表达“加入其他 App”。应与新 API 组合；旧系统降级基础
NSWindowCollectionBehaviorFullScreenAuxiliary
macOS 10.7+		窗口可以和全屏窗口显示在同一个 Space。老方案通常与 canJoinAllSpaces 组合。旧系统降级；单独使用的跨应用保证较弱
NSWindowCollectionBehaviorMoveToActiveSpace窗口激活时移到当前 Space。与 canJoinAllSpaces 是互斥选择，而且“激活”可能抢焦点。不适合作为常驻时钟主方案
NSFloatingWindowLevel控制同一 Space 内的前后层级。AWT alwaysOnTop 已映射到它。保留即可；不建议升到 screen-saver level

建议行为位：

// macOS 13+
collectionBehavior = [.canJoinAllApplications, .canJoinAllSpaces]
level = .floating

// macOS 10.7–12 fallback
collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]
level = .floating

screenSaver level 会盖住更多系统 UI，不符合普通时钟覆盖层的最小权限/最小干扰原则；floating 足以盖住正常级别的全屏内容。

3. “当前屏幕”的三种定义

定义获取方式权限与代价
鼠标所在屏幕（推荐默认）MouseInfo.getPointerInfo().device.defaultConfiguration纯 Java、无需授权；含全屏窗口所在显示器，只要鼠标位于该显示器
键盘焦点/当前 App 所在屏幕原生 NSScreen.mainScreen，再按显示器 frame 或 display ID 映射到 AWT无需辅助功能权限；需要原生桥接。Apple 将其定义为包含 key window 的屏幕
前台 App 的 AX focused windowAccessibility API 查询焦点窗口 frame需要用户授予“辅助功能”权限，维护成本高；本项目通常没必要

建议产品语义明确为“鼠标所在屏幕”。它可预测、无权限弹窗，也天然适配多显示器。若以后要求“键盘正在操作的 App 所在屏幕”，再增加 NSScreen.mainScreen 模式。

4. 可实施路径对比

路径改动能力判断
A. 纯 Compose/AWT 使用低层 DialogWindow(create = …) 创建 ComposeDialog(pointerGraphicsConfiguration)，显示前设置 type = Window.Type.POPUP、focusableWindowState = false、autoRequestFocus = false。 当前显示器可完整解决。OpenJDK 会为 POPUP 自动设置 fullScreenAuxiliary 并使用 orderFrontRegardless。 适合第一阶段 PoC；没有设置 canJoinAllApplications，不应承诺所有 macOS/全屏 App 都稳定。
B. 薄 AppKit 桥接 增加一个 macOS 专用 Objective-C/Swift 小桥，拿到底层 NSWindow 后在 AppKit 主线程设置 collection behavior；UI 仍由 Compose 渲染。 完整使用公开 AppKit 语义，支持 macOS 13+ 精确跨应用全屏，旧系统可降级。 推荐正式方案。原生层很薄，跨平台主体不变。
C. 反射 OpenJDK 私有 peer + JNA 通过 AWTAccessor/LWWindowPeer/CPlatformWindow 取 NSWindow 指针，再调用 Objective-C runtime。 能实现，但依赖 sun.*、--add-opens/--add-exports 和 JDK 内部结构。 不推荐生产使用；JDK 升级脆弱，且 AppKit 主线程处理仍需额外解决。
D. macOS 独立原生窗口/重写 Swift/AppKit 创建 NSPanel 并自行绘制时钟，或迁移 Kotlin/Native。 控制最完整。 现阶段成本明显过高，除非未来 macOS 版本要独立演进。

5. 推荐落地顺序

  1. 先做纯 JVM PoC：切换到 Compose 低层 DialogWindow(create/update)；在 create 阶段用鼠标所在 GraphicsConfiguration 创建窗口并设置 Window.Type.POPUP，避免 setType 在窗口 displayable 后抛异常。
  2. 验证矩阵：内建屏/外接屏、各屏普通桌面、Safari/Chrome/视频播放器原生全屏、全屏 App 切换、Mission Control“显示器具有单独的空间”开/关、休眠唤醒和拔插显示器。
  3. 正式补原生桥：macOS 13+ 设置 canJoinAllApplications | canJoinAllSpaces；macOS 12- 设置 canJoinAllSpaces | fullScreenAuxiliary。所有 AppKit 修改都在主线程完成。
  4. 监听环境变化：显示器配置变化时重新计算右下角；如果窗口采用单一实例跟随策略，Space 变化可监听 NSWorkspaceActiveSpaceDidChangeNotification，鼠标跨屏则按低频轮询或用户交互时更新。
  5. 保持非侵入：focusable = false、isAutoRequestFocus = false，不要调用 makeKeyAndOrderFront，避免切换全屏时夺走当前 App 焦点。

6. 推荐的第一阶段代码形态（示意）

val screen = MouseInfo.getPointerInfo()
    ?.device
    ?.defaultConfiguration

DialogWindow(
    create = {
        ComposeDialog(graphicsConfiguration = screen).apply {
            type = Window.Type.POPUP          // 必须在首次显示前
            isFocusableWindowState = false
            isAutoRequestFocus = false
            isUndecorated = true
            background = Color(0, 0, 0, 0)
        }
    },
    update = { dialog ->
        dialog.isAlwaysOnTop = true
        // 使用 screen.bounds + Toolkit.getScreenInsets(screen)
        // 计算目标显示器可用区域内的右下角坐标
    },
    dispose = ComposeDialog::dispose
) { /* clock content */ }

这段只表达结构，不是最终补丁。尤其需要保留当前尺寸随文本变化的状态同步，并处理混合缩放显示器的 AWT user-space 坐标。

7. 风险与边界

  • DRM/受保护内容：AppKit 覆盖层与屏幕录制不是一回事，但某些播放器或受保护视频可能使用特殊窗口层级；不建议用更高的 screen-saver level 强行覆盖。
  • Stage Manager：canJoinAllApplications 正是 Apple 从 macOS 13 起为 Stage Manager 与全屏跨应用加入语义提供的行为位，比旧的 fullScreenAuxiliary 更准确。
  • 多个显示器同时显示：单个 NSWindow 只有一个几何位置。若需求变为“每块屏幕都显示”，应为每个 GraphicsDevice 创建一个窗口，而不是移动同一个窗口。
  • Spaces 是私有体系的一部分：不要依赖 CGS 私有 API 枚举/切换 Space ID；公开的 collection behavior 已覆盖本需求，也更适合签名、公证与长期维护。
