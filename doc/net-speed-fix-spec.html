FLOATCLOCK / FIX SPEC / 2026-11-17

恢复 macOS 下载速度显示

macOS 改用原生路由统计，按物理接口与根路由去重；上下行共用同一来源，所有时钟窗口共享一次采样。

状态：已实现，28 项 Kotlin 测试、5 项原生回归、发布混淆及真实 JNI 自动恢复验证通过。验证环境：本机 macOS 27.2.1，build 26B131。

01 / 原因与证据

当前 NetSpeedMonitor 从 OSHI 读取网卡累计收发字节，再对相邻采样做差。显示层正确绑定下载与上传；故障发生在本机 en0 的 legacy 接收计数：实际下载成功，系统返回的接收累计值仍为 0。

检查本机结果说明
受控 HTTPS 下载HTTP 200，下载 257,229 字节；旧计数 RX 0 → 0，TX 18,329,766,025 → 18,330,130,086。有真实接收流量，只有旧 RX 计数失效。
OSHI / netstat / getifaddrs / IFMIB所有入口的 en0 RX 均为 0；64 位 IFMIB 也如此。更换 Java 映射或公开 ifnet 查询入口不能恢复这台机器的下载读数。
IOKit / Skywalk网卡类为 IOSkywalkLegacyEthernetInterface；IONetworkStatsKey 全零；Skywalk 可见接收包计数，但所查接口没有可用的无提权接收字节数。本次采用另一份已验证的字节统计。
原生 NetworkStatistics 路由探针无需 root，连续得到 64 位 RX/TX；同一下载窗口根路由 RX 增加 395,346 字节，包含后台流量。替代来源能在原来源失效时记录接收量。
父子路由计数相同窗口直接汇总全部路由，RX 增加 790,548 字节，约为根路由的两倍。必须依据父子关系去重。
本机通信127.0.0.1 的 4 MiB 传输未产生对应物理流量；访问自己的局域网 IP 则记入一个无 RTF_LOCAL 的 en0 根路由。按本机地址过滤后，该传输被剔除 4,215,432 字节，同窗口保留的外部 RX 仅 79,785 字节。本机地址过滤已复测有效，不能只过滤 loopback 网卡或依赖标志位。

确定的原因是本机物理网卡的 legacy RX 计数没有随接收流量更新。Skywalk 接收链路未同步维护旧计数是机制推测；目前不能进一步归责到操作系统、驱动或某个网络扩展。btop 的同类问题报告提供了另一台 macOS 27 设备的旁证。

同时修正 4 GiB 回绕漏报

当前 OSHI 6.6.5 的 macOS 实现把字节数截为 32 位；单个方向累计跨过 4 GiB 时，读数会回绕。现有“先汇总、后求差、负数归零”会使该轮速度漏报。6.9.0仍沿用这一实现。macOS 绕开该路径、保留原生 64 位计数，可一并消除这个问题。

02 / 选定修法

推荐：通过现有 macOS 原生库动态接入 NetworkStatistics 的 route provider。每秒读取一次完整快照，仅统计合格物理接口上的根路由，排除本机地址。Windows、Linux 继续使用 OSHI。macOS 统一使用路由来源，不靠“上传多、下载少”的启发式切换统计源。
路径结果与取舍
升级 OSHI / 换公开 ifnet 入口本机已证明同一 RX 计数失效，不能解决持续零速。
常驻 nettop 子进程可以读到流量，但路由 CSV 展示不如原生描述直接提供稳定的 route ID、parent ID 与 ifindex；还要维护进程和文本解析。保留作排查工具。
原生 route provider选用。本机探针已验证，无需提权；直接获取路由身份、层级和 64 位字节数，可控制去重及生命周期。

统计口径定为物理接口上的 IP 路由收发速度。通过排除隧道内层和本机通信，避免代理链与回环造成的重复；下载、上传均来自同一口径。

03 / 采集与计算约定

原生路由快照 → 物理接口、根路由、本机地址过滤 → 逐源差分 → 共享 StateFlow → 所有时钟窗口

路由选择

  1. 读取描述中的 route ID、parent ID、ifindex、flags、目的地址及掩码。通过 ifindex 映射系统网卡，延续现有虚拟接口排除范围，排除 loopback、utun、awdl 等。
  2. 仅选择明确 parent ID == 0 的根路由。子路由已累计到父路由，不再单独相加；即使只使用默认路由也会漏掉局域网和其他独立路由，因此应选择全部合格根路由。
  3. 排除 RTF_LOCAL，并依据当前网卡地址排除目的地址等于本机 IPv4/IPv6 地址的 host route。通过 /32、/128 掩码识别 host，不能只看 RTF_HOST；地址作数值比较，IPv6 link-local 同时处理 scope。只匹配本机地址，不按整个局域网网段过滤。每轮采样刷新网卡与本机地址，直接覆盖网络配置变动。
  4. 明确区分字段缺失与数值为 0。描述未就绪的路由不被当成根；已知子路由直接排除，无需等待其父源进入集合；已知非物理接口也先排除。候选根数据不完整时显示等待状态，并按下述恢复规则处理。

Apple 的 nstat_route_rx / nstat_route_tx沿 rt_parent 更新祖先计数，支持上述根路由去重规则。

逐源计算

source = macOS: route ID + ifindex
         Windows / Linux: 系统网卡标识

elapsed = 本次与上次采样的单调时间差
down = Σ(有效且连续的源.recv - 上次该源.recv) / elapsed
up   = Σ(有效且连续的源.sent - 上次该源.sent) / elapsed
  • macOS 全程使用 64 位计数；采样时间使用 System.nanoTime()。调整系统时间不影响速率。
  • 每个根路由分别保存基线后求和，不能对全体源的历史累计总和直接求差。新出现或计数重置的源只建立基线；移除的源清理基线，避免网络切换时产生巨幅尖峰或把其他源的速度抵消。
  • 同一轮上下行必须来自同一个完整快照。采集失败的源不复用旧计数伪造正常速度；恢复后重新建立基线。
  • 单次查询未完成时不重叠发起下一次查询。使用实际单调时间间隔计算，不能固定除以 1 秒。

线程、生命周期与显示

  • 将 NetSpeedMonitor 从每个 FloatClockContent 上移到 application 会话层。所有显示器订阅同一个 StateFlow；打开“显示网速”时启动，关闭或退出时停止并释放原生 manager。
  • 原生 manager、路由表和回调由同一条专用串行队列管理。Kotlin 在 IO 协程请求采样，原生查询完成后交付不可变快照；EDT 与 AppKit 主线程不等待采样完成。Objective-C 类统一使用 FloatClockNetwork 前缀，与系统 framework 的全局类名隔离。
  • 启动初始化及采集失败显示 ↓ -- ↑ --；完整有效的空闲样本显示 0 B/s。可用状态可通过 StateFlow<NetSpeed?> 表达，无需增加配置开关。
  • 动态加载 framework 并检查所需符号。初始化失败时按采样间隔自动重试；未恢复有效速度期间累计 3 次采样失败，先关闭旧 source，下一轮创建新会话并重建基线。首次成功基线继续显示 --，实际产生有效速率后才清空失败预算；因此失败与基线交替也能自动恢复。原生查询超时后关闭旧 manager，再创建新会话，避免叠加在飞查询。
  • 遵循现有 SLF4J 规范：固定简单名称 logger，异常作为最后参数。失败类型或首行原因变化时记录一次 WARN；原生错误首行包含 route ID、ifindex，第二行包含当前代数、路由代数及计数字段就绪状态；代数变化不重复刷日志。重建和恢复使用 DEBUG。JNI 将错误传给 Kotlin 记录。

05 / 验收

实施时优先验证会导致错数的分支；单元测试使用明确字节差和时间差，不依赖实时联网。

场景通过标准发现失败后的处理
计数超过 4 GiB；多个源并行64 位值连续；一源重置或新增不影响其他源的增量。修正计数映射与逐源基线，禁止总和直接做差。
根路由、子路由、缺失描述父子只计一次；缺失 parent 不被当成 0；局域网独立根路由保留。修正根路由选择及快照就绪条件。
回环、本机局域网 IP、远端局域网 IP前两者不产生对应网速；第三者正常计入。修正 host route 与本机地址匹配，不扩大为网段过滤。
初始化、采集失败、恢复、关停重启等待/失败为 --；有效空闲为 0；未恢复速度期间累计 3 次失败后自动重建，初始化失败自动重试；恢复无历史累计尖峰；停止后释放采集资源。修正状态转换、基线重建和原生生命周期。
本机持续下载与上传，IPv4 / IPv6两方向均随受控传输变化；与同窗口 nettop 根路由口径一致；不要求等于文件净载荷。先定位来源、过滤与采样窗口，再修采集层。
CorpLink / 其他实际使用的 VPN；网络切换与睡眠唤醒内外层不重复；接口变化无累计量尖峰；唤醒后重新得到有效样本。针对真实接口与路由变更修正过滤和基线。
多屏、网速开关、发布混淆包所有窗口数值一致且只有一个采样器；关闭后无查询；发布包能加载 JNI 和原生资源。修会话层持有方式、停止逻辑或打包保留规则。
Windows / Linux既有 OSHI 网卡读数及显示可用，未引入 macOS framework 加载。修平台入口分流；在实际平台完成回归。

06 / Limitations

  • 私有系统 API：NetworkStatistics 不承诺跨版本 ABI 稳定，需要在支持的 macOS 版本上验证。当前方案面向已有桌面分发方式；App Store 分发需要另行评估。符号检查只能发现缺失入口，不能替代实机兼容性验收。
  • 统计口径：路由计数是 IP 层字节，含其自身的统计语义，不等于文件净载荷或完整物理链路帧字节。ARP、以太网/Wi-Fi 帧开销不计入，不用于计费。IPv4/IPv6 路由计数入口可参见 ip_input.c、ip_output.c、ip6_input.c 与 nd6.c。
  • 切换窗口：新建或重置源需要一轮基线；路由删除时尚未采到的尾部流量可能丢失。目标是稳定的实时显示，不做历史累计流量账本。
  • 验证边界：本机正式采集、包内混淆 JNI 和注入持续失败后的自动恢复已验证。多日运行、完整 VPN 模式、睡眠唤醒、旧版 macOS 与 Windows/Linux 仍需实机观察；本次包内采集验证使用系统 JDK 21 加载应用包 JAR。底层 legacy RX 计数未更新的具体系统责任仍未确定。

本机诊断材料：受控下载与回环记录、本机地址过滤记录、原生采集探针、探针开销。这些材料位于被忽略的 build 目录，clean 后可被删除；关键测量结果已保留在本方案正文。
